## 2026-09-05 — Backend environment

A local Supabase stack (Docker + WSL) was built, seeded and verified first, then
deliberately abandoned the same day. Recorded because the reasoning matters more
than the outcome, and because the reversal itself was the decision.

| #   | Decision                                                                                                                           | Why                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | See                    |
| --- | ---------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------- |
| D27 | **Supabase Cloud is the only backend. No local stack, no Docker, no WSL.**                                                         | The point of a backend right now is to be reachable _from a phone_. A local stack is reachable from the dev machine and then needs a LAN IP for a device, `10.0.2.2` for an Android emulator, and different values again for an EAS build handed to a bandmate. One hosted project removes that whole class of environment juggling, and removes ~7 GB of images and a 4 GB WSL VM from the machine. Accepted cost: no offline development, migrations run against a live database, and a free-tier project pauses after a week idle | `.env.example`         |
| D28 | **The schema starts empty.** `0001_init.sql` and `seed.sql` were deleted rather than pushed to the cloud project                   | Every table should be introduced deliberately, as the feature that needs it is built, rather than inherited wholesale from a document. The 463-line schema is not lost — it is in git at `88b39e7` and can be reintroduced a table at a time. Note the seed could never have run on a hosted project anyway: it writes directly to `auth.users`, which only the local stack permits                                                                                                                                                  | git `88b39e7`          |
| D29 | **The app is one screen: a connection check.** The tab skeleton, join route and performance route were removed                     | v0.0 has exactly one thing worth knowing — can the device reach the database. Screens for features that do not exist made that answer harder to see, not easier                                                                                                                                                                                                                                                                                                                                                                      | `app/index.tsx`        |
| D30 | **The health probe selects from a table that deliberately does not exist, and classifies on HTTP status, never on the error code** | With no tables there is nothing legitimate to select, but a `PGRST205` still proves the gateway authenticated the key and PostgREST answered from a schema cache built by reading Postgres. Status is the only trustworthy signal: postgrest-js does not throw when a request never lands (status `0`), and a rejected key returns a **null** error code (status `401`) — so branching on the code blames the network for what is really a bad key. Both shapes are pinned by tests                                                  | `src/features/health/` |

## 2026-09-09 — Sign-in

| #   | Decision                                                                                                                   | Why                                                                                                                                                                                                                                                                                                                                                                                        | See                                                               |
| --- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------- |
| D31 | **Email + password is the way in, and sign-up is disabled**                                                                | Both passwordless methods need a transactional email provider before anyone can sign in once, and auth blocks every other v0.1 story. Email OTP stays the target and reuses everything built here                                                                                                                                                                                          | [ADR-0008](../tech/adr/0008-email-password-auth-now-otp-later.md) |
| D32 | **The session lives in the OS keystore, split across numbered entries**                                                    | A refresh token is a bearer credential and belongs in the Keychain / EncryptedSharedPreferences, never in AsyncStorage. But SecureStore documents a 2048-byte ceiling on Android and a Supabase session is routinely larger, so the value is chunked behind a small index. The index carries the expected length, which is what makes a torn write detectable rather than silently corrupt | `src/lib/secureStorage.ts`                                        |
| D33 | **Percent-encode before chunking**                                                                                         | Chunking by character length is only chunking by byte length if every character is one byte. A display name in Japanese would put ~5400 bytes into an "1800-character" chunk and hit the limit the chunking exists to avoid                                                                                                                                                                | `src/lib/secureStorage.ts`                                        |
| D34 | **Route guards, not redirects.** `Stack.Protected` decides which half of the app exists; no screen navigates on auth state | A screen that pushes a route after signing in is a second source of truth for "am I signed in", and the two disagree the first time a token expires. Expo Router removes a guarded route from the navigator entirely, so there is no signed-out state in which the app's screens are merely hidden                                                                                         | `app/_layout.tsx`                                                 |
| D35 | **The query cache is cleared on sign-out**                                                                                 | Every cached row was fetched under the previous identity. On a tablet shared between bandmates, keeping it shows one musician's data to the next one to sign in                                                                                                                                                                                                                            | `src/features/auth/AuthProvider.tsx`                              |
| D36 | **A wrong password and an unknown account get the identical answer**                                                       | Distinguishing them turns the sign-in screen into a way to enumerate who has a Jamly account, and helps nobody: the musician who typo'd their address is not served by either message                                                                                                                                                                                                      | `src/features/auth/api/authErrors.ts`                             |
| D37 | **No password-strength rule on the sign-in field.** Strength is enforced server-side, in the dashboard                     | A minimum length checked at sign-in locks out whoever chose their password before the rule existed, and publishes the shape of every password in the system. Strength belongs where a password is chosen                                                                                                                                                                                   | [ADR-0008](../tech/adr/0008-email-password-auth-now-otp-later.md) |
| D38 | **`profiles` is the first table, and `plan` is not writable by the client**                                                | The row-level-security policy decides which _row_ a musician may edit; a column-level grant decides which _columns_. Without it, a client with a perfectly valid session could set its own `plan` to `pro` — a distinction that stops being academic the moment money is involved                                                                                                          | `supabase/migrations/20260909220000_profiles.sql`                 |
| D39 | **The token refresh timer runs only in the foreground**                                                                    | Left running, it wakes the app to renew a token nobody is using. A phone in a gig bag through a four-hour load-in should be asleep                                                                                                                                                                                                                                                         | `src/features/auth/AuthProvider.tsx`                              |
| D40 | **Trigger functions live in a `private` schema, never in `public`**                                                        | Everything in `public` is a PostgREST endpoint, so a `security definer` trigger function there is callable as `/rest/v1/rpc/…` by anyone holding the publishable key. Caught by `supabase db advisors`, which is now worth running after every migration. Moving them out is more durable than revoking `execute` grant by grant — a schema nobody is exposed to cannot be forgotten       | `supabase/migrations/20260909223000_…sql`                         |
| D41 | **Auth configuration is `config.toml` + `config push`, not dashboard clicks**                                              | Same reasoning as migrations: an untracked dashboard change is drift nobody can reconstruct. `config pull` was run first so the file is a true record of the project, and `config diff` shows exactly what a push would change. Two settings are declared so far — signups off, minimum password length 10                                                                                 | `supabase/config.toml`                                            |

## 2026-10-30 — Working with agents

| #   | Decision                                                                                                 | Why                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | See                                                                                                                                              |
| --- | -------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| D42 | **Agents never write to the live Supabase project.** They write migration files; Elia applies them       | A migration pushed to the cloud project is the one irreversible step in this repo: there is no local stack to try it on first (D27). A line in `CLAUDE.md` only makes the mistake less likely, so it is also denied in `.claude/settings.json` — and the real boundary is that cloud sessions are never given Supabase credentials, which no deny rule can be routed around                                                                                                                                                                                                                                                                                      | `CLAUDE.md`, `.claude/settings.json`                                                                                                             |
| D43 | **Agents work through PRs only.** One issue, one branch, one PR; merge is Elia's                         | Delegating the code is not delegating the product. PRs target `dev`; `dev`, `staging` and `main` are protected so this holds even when an agent ignores the instruction                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | `CLAUDE.md`, branch protection                                                                                                                   |
| D44 | **The definition of done names who holds each line**                                                     | A cloud session can run typecheck, lint and tests, but cannot check two platforms, offline reads or dark legibility. Saying so stops an agent from claiming what it cannot have verified, and tells Elia exactly what to try on a device                                                                                                                                                                                                                                                                                                                                                                                                                         | `CLAUDE.md`                                                                                                                                      |
| D45 | **Issues are written to a template** that forces acceptance criteria, out-of-scope and settled decisions | An agent builds what the issue says. The template is where scope collapse (R1) gets stopped before any code exists                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | `.github/ISSUE_TEMPLATE/`                                                                                                                        |
| D46 | **Labels carry the workflow state; the GitHub Project is for planning only**                             | A Claude cloud session reaches issues and labels through the REST API but not GitHub Projects. Whatever an agent must read or signal — ready, working, blocked, needs a device check — has to be a label, or the agents can't see it. Labels are declared in `.github/labels.yml` so they can be recreated and reused                                                                                                                                                                                                                                                                                                                                            | [42-project-board](42-project-board.md)                                                                                                          |
| D47 | **The repository is public, and all rights are reserved**                                                | Branch protection and rulesets are not available on a private repository under GitHub Free, and they are the boundary D43 relies on. Public makes them available at no cost; the history was scanned for secrets first (none — only placeholders and the publishable key, which ships in the app bundle anyway). The `LICENSE` that came with the Expo template was MIT under Expo's copyright, which would have made the code free to reuse; it is replaced with all-rights-reserved. Starting restrictive keeps every option open: as sole copyright holder, Elia can later relicense (AGPL, FSL…), while a version published under an open licence stays open | `LICENSE`                                                                                                                                        |
| D48 | **Push deny rules match the branch name after any separator, and a push must name its branch**           | Deny rules match command text. The first version caught only `git push origin dev …`; a probe found 9 of 12 ways to push to a protected branch passing (`HEAD:dev`, `+dev`, `--dry-run origin dev`, a bare `git push`…). They now match ` dev`, `:dev`, `/dev` and `+dev` (same for `staging`, `main`) and deny any push that doesn't say where it goes. Also learned: project settings load only when the session is rooted in the repo — a session opened from a parent folder has no deny rules at all. Still a guardrail: the ruleset is what holds                                                                                                          | `.claude/settings.json`, #4                                                                                                                      |
| D49 | **Agents recover before they stop**                                                                      | Agents came back with "it doesn't work" from one error line, when the alternative was one command away (`gh auth status` called a valid token invalid; `gh api user` worked). Each one cost Elia an interaction. The rule is account-wide and lives in agent-kit; the line in `CLAUDE.md` makes it hold even where the account file is missing                                                                                                                                                                                                                                                                                                                   | `CLAUDE.md`, [agent-kit ADR 0010](https://github.com/ferrarolabs/agent-kit/blob/main/docs/decisions/0010-agents-recover-before-they-escalate.md) |
| D50 | **CI fails on Prettier; generated types and ADRs are not formatted**                                     | Without a failing check, formatting drifted from 2 files to 45 in a few days. `src/types/database.ts` is regenerated after every migration, so formatting it would be undone each time. ADRs are never edited, and reformatting one broke its code sample (ADR-0004). The CI job keeps its name, because branch protection requires the check by name                                                                                                                                                                                                                                                                                                            | `.prettierignore`, `.github/workflows/ci.yml`, #8                                                                                                |

## 2026-10-31 — What I play in this band (story A4)

| #   | Decision                                                                                                                | Why                                                                                                                                                                                                                                                                                                  | See                                                                                                                     |
| --- | ----------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| D51 | **Instruments are edited on my own roster row on `BandHome`, behind an "Edit" button — not in a Me tab or `MyProfile`** | Instruments live on the membership, so they are per band: a list in a profile screen would have to ask "which band?" first, or pretend to be global. The roster is where the band reads them, so it is where I change them. Only my own row has the button. Confirmed by Elia, 2026-10-31            | `src/features/band/components/MyRosterRow.tsx`, [21-information-architecture](../design/21-information-architecture.md) |
| D52 | **Tap-to-add suggestions (drums, bass, guitar, keys, vox) plus free text**                                              | Instruments are free-form strings, not an enum (13-domain-model). Suggestions make the common case one tap; free text covers "occasional harmonica". Entries are trimmed and de-duplicated ignoring case before they are saved, first spelling wins. Confirmed by Elia, 2026-10-31                   | `src/features/band/instruments.ts`                                                                                      |
| D53 | **An empty list is valid, the default, and never prompted for**                                                         | No "complete your profile" prompts (20-design-principles). The drummer who never opens the editor loses nothing                                                                                                                                                                                      | `src/features/band/components/InstrumentsEditor.tsx`                                                                    |
| D54 | **The save is not optimistic, and an update that comes back with no row is a refusal**                                  | A failed save must leave the previous list on the roster, so the cache changes only after the database says yes. Row-level security does not raise on an update it filters out — it updates nothing — so the repository asks for the row back and treats none as "you may no longer be in this band" | `src/features/band/api/band.repo.ts`                                                                                    |
